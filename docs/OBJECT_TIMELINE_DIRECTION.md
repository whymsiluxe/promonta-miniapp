# Object timeline direction (Worker UX V2, Этап 9)

Docs-only per plan: не строить desktop CRM/WhatsApp integration/BIM/customer
portal/CompanyCam clone сейчас. Задача этого этапа — не создать новый тупик:
задокументировать текущее состояние Object History, найти реальные пробелы,
и зафиксировать правило, что будущие действия расширяют этот существующий
механизм, а не заводят параллельное history-хранилище.

## Что уже есть

Единый механизм: `backend/main.py:2121` `_append_object_history()` пишет в
per-object историю (`GET /api/objects/{object_id}/history`, `main.py:2161`).
`_append_object_history_best_effort()` (`main.py:2153`) — тот же вызов,
проглатывающий исключения, чтобы сбой логирования не ронял основной запрос.

Каждая запись: `{kind, title, subtitle, actor_name, meta, at}`.

## Существующие event kinds (проверено grep по коду, не по памяти)

| kind | Где логируется |
|---|---|
| `worker_assigned` | назначение работника на объект/этап (main.py:2297, 2787) |
| `document_uploaded` | загрузка документа объекта (main.py:3926) |
| `object_status_changed` | смена статуса объекта (main.py:4038) |
| `broadcast_sent` | объявление в чат объекта (main.py:6042) |
| `stage_status_changed` | смена статуса этапа (main.py:6790) |
| `stage_completed` | завершение этапа (main.py:6843) |
| `defect_created` | создание дефекта/тикета Mängel (main.py:7573) |
| `finish_submitted` | завершение смены (checkin finish) (main.py:8380) |

## Найденный пробел (реальный, не гипотетический)

Проверено прямым grep по каждому эндпоинту — ни один из следующих не вызывает
`_append_object_history`/`_append_object_history_best_effort`:

- `POST /api/checkin/start` (main.py:7953) — **старт смены не попадает в
  историю объекта вообще**, при том что `finish_submitted` (её же смены)
  логируется. Асимметрия: тайм-лайн объекта показывает, когда смена
  закончилась, но не когда началась.
- `POST /api/checkin/{session_id}/pause` (main.py:8115) — пауза/резюме смены
  не логируются.
- `POST /api/tasks` (main.py:7365) — создание Потребности не попадает в
  историю объекта (хотя `defect_created` для Mängel — попадает).
- `POST /api/daily-plan` (main.py:9687) — создание DailyPlan не логируется.
- `POST /api/daily-plan/{plan_id}/accept` (main.py:9445) — принятие плана
  работником не логируется.

Это не баги (ничего не ломается), но это ровно те события, которые Этап 5
(«Сегодня») и будущий Этап 7 («Обзор» → recent activity) хотели бы показывать
в едином тайм-лайне объекта. Сейчас их там физически нет.

## Правило для будущих действий (обязательное, не рекомендация)

Любое новое действие, которому нужен "след" на объекте (в любом будущем
Auto-Bautagebuch/timeline/report-центре) добавляет вызов
`_append_object_history_best_effort(object_id, '<new_kind>', ...)` в
существующий `main.py`. **Не создавать** отдельный JSON-файл/таблицу/эндпоинт
для истории — это создало бы вторую parallel-реализацию того, что уже есть,
и тайм-лайн объекта расщепился бы на два несинхронных источника правды.

Если для нового kind нужен UI-рендерер записи — расширять существующий
рендер `GET /api/objects/{object_id}/history` consumer (проверено grep:
эндпоинт потребляется из `frontend/js/objects.js`, конкретное имя
рендер-функции — проверить точным grep перед использованием, этот документ
подтверждает только backend-контракт выше, не текущий UI-код построчно).

## Не входит в этот этап

Заполнение пробелов выше (добавление `_append_object_history` вызовов в
checkin start/pause, tasks create, daily-plan create/accept) — реальная
работа, но не "docs only". Явно отложено на отдельный, будущий шаг
(потенциально часть Этапа 7 «Обзор» — recent activity, если тайм-лайн
объекта станет частью того экрана и пустые дыры станут заметны визуально).

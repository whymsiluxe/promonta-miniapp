# Object Detail V2 — Обзор|Работа|Медиа|Чат (Worker UX V2, Этап 7)

**Статус: docs only, миграция НЕ выполнена в этой сессии.** План прямо
разрешает это для рискованных переключений: "если переключение рискованно —
reusable panels + follow-up doc вместо реального рефакторинга". Ниже —
почему риск реально высокий (не гипотетически), и точный план миграции для
следующей сессии.

## Первое расхождение с планом: "8 вкладок" не существует

План (`UNIFIED_STEP_BY_STEP_PLAN_v1.1.md`, Этап 7) говорит "4 зоны вместо 8
вкладок". Проверено кодом (не по памяти): реальность другая.

- Верхнеуровневых табов сейчас **3**: Чат / Инфо / План работ
  (`OBJ_DETAIL_TAB_ORDER = ['chat', 'info', 'stages']`, `objects.js:1427`,
  markup `#obj-detail-tabs`, `app.html:8833-8837`).
- История в коде прямо документирует путь до этого: было 6 плоских табов
  (24.07) → owner попросил свести до 2 (25.07) → потом до 3, добавив
  "План работ" (29.07), Потребности влиты в "Инфо" как секция.
- То, что план, вероятно, насчитал как "8 вкладок", — это 10+ независимых
  секций, отрендеренных ОДНИМ вертикальным скроллом внутри таба "Инфо":
  control-center, photo-upload, status-switch, team&shifts, description,
  works (Объёмы/Задачи под-таб), defects summary, docs summary+viewer,
  needs, budget, task kanban, history.

Вывод: маппинг "8 табов → 4 зоны" как задача не имеет смысла в буквальном
виде — реальная задача "перегруппировать 3 таба + 11 секций в 4 зоны".

## Почему это НЕ безопасный 1-проходной рефакторинг (конкретные основания)

1. **owner/worker не разделены архитектурно.** Это не два дерева рендера —
   одна и та же функция (`renderObjectInfoTab()`, `object-info.js:11`)
   содержит owner-контент через inline-тернарники
   (`currentRole === 'owner' ? html : ''`) — 14 таких проверок в
   object-info.js, 6 в objects.js. Переставить секции по новым зонам без
   риска задеть owner-путь означает вручную пройти каждую из ~20 проверок.
2. **Чат-панель физически перемещает DOM-узлы между родителями**
   (`embedObjectChat`/`unembedObjectChat`, `object-info.js:2116-2239`,
   ~124 строки) — с историей минимум 2 задокументированных тонких багов
   (inline-style specificity, stale selector после первого embed, тот же
   класс проблемы что уже один раз ловили на `applyRoleNav()`). Перенос
   этой логики в новую зону "Чат" без сохранения 1:1 текущего пути внедрения
   рискует их воскресить.
3. **Порядок секций хардкожен через DOM-якоря**, не декларативный список:
   `renderObjectBudgetSection()`/`renderObjectTaskKanbanSection()`/
   `renderObjectHistorySection()` вставляются `insertAdjacentHTML('afterend',
   ...)` относительно id соседней секции, цепочкой промисов (`objects.js:1130,
   1332-1335`), из ДВУХ разных файлов. Перегруппировка по зонам сломает эти
   якоря, если вставку не переписать декларативно.
4. **Тестовое покрытие почти нулевое** — единственная зацепка во всём
   `tests/*.py`: `test_chat_frontend_contract.py:96`, один CSS-selector
   assert. Ни число вкладок, ни структура `#obj-detail-tabs`/
   `obj-works-subtabs`/`obj-control-center` ничем не защищены. Регрессия не
   будет поймана автоматически — весь риск ложится на ручное QA поверх
   ~3000 переплетённых строк (object-info.js 2239 строк + релевантная часть
   objects.js ~750 строк).
5. **"Обзор" уже существует, но owner-only.** `_renderObjControlCenter()`
   (`object-info.js:280-384`) — готовый dashboard (плитки На смене/Не
   начали/Просрочено/Дефекты/Документы/План + alert-rows), но целиком за
   `currentRole === 'owner' ?` (`object-info.js:40`). Для worker-версии
   "Обзора" нужно осознанное решение, что из него безопасно показать worker
   (team&shifts тоже owner-only целиком — не факт что worker должен видеть
   состав смен других людей без спроса).
6. `#stages-view` (отдельный standalone экран этапов, `app.html:8851`,
   `objects.js:826-888` `openStagesView`/`closeStagesView`) выглядит
   полумёртвым/legacy — не найдено активных вызовов из текущих обработчиков
   кликов (текущий путь — `openObjectDetail(..., 'stages', ...)`,
   `objects.js:452`). Судьбу этого файла нужно подтвердить ОТДЕЛЬНО, не
   внутри Этапа 7 — трогать неясный код одновременно с реструктуризацией
   удваивает риск.

## Целевой маппинг секций → 4 зоны (для следующей сессии)

| Новая зона | Что туда переезжает (источник, без переписывания логики) |
|---|---|
| **Обзор** | `_renderObjControlCenter()` (снять/пересмотреть owner-гейт — отдельное решение, не тихое снятие), `renderObjectHistorySection()` (recent activity — уже видим worker+owner), active shift status (переиспользовать `resolveWorkerShiftState()`, тот же паттерн что Home), budget — **owner-only где нужно**, не менять гейт |
| **Работа** | DailyPlan (переиспользовать `_openPlanCard()`/`renderDailyPlan()` из today-plan.js, НЕ второй рендер), stages/roadmap (`object-info.js:835-2115`, включая drag-reorder — самый большой блок, ~1280 строк, переносить последним, после того как более мелкие секции подтвердят паттерн), `renderObjectTaskKanbanSection()`, needs-секция, defects summary, checklists (per-stage roadmap) |
| **Медиа** | photo-upload (owner-only сейчас — пересмотреть отдельно, план хочет worker Фото-quick-action, см. Этап 6 уже реализован отдельно от object-detail), docs summary+viewer |
| **Чат** | `embedObjectChat`/`unembedObjectChat` — переносить С МАКСИМАЛЬНОЙ осторожностью, 1:1 сохраняя текущий DOM-путь, не переписывая механизм перемещения узлов |

## Что делать в следующей сессии (конкретные шаги, не абстракция)

1. Подтвердить/закрыть судьбу `#stages-view` (legacy?) — отдельный, более
   мелкий commit ДО начала реструктуризации, чтобы не тащить неопределённость
   в больший рефакторинг.
2. Написать decision (docs/DECISIONS.md запись) по owner-only секциям
   Обзора: какие worker увидит как есть, какие в урезанном виде, какие не
   увидит вообще — ДО кода, не по ходу.
3. Мигрировать зоны в порядке возрастания риска: Медиа (наименьшая связность)
   → Работа (kanban/history/needs — уже независимые секции) → Обзор
   (требует owner-гейт decision) → Чат (наибольший риск, переносить
   последним, с ручным QA на реальном iPhone Telegram сразу после).
4. На каждом шаге — добавлять contract-тест (source-assertion, как весь
   остальной repo) ДО переноса, фиксирующий текущее поведение, чтобы перенос
   можно было проверить, а не полагаться только на ручной клик.
5. Owner nav/owner object-detail поведение не меняется вообще — если
   какая-то секция технически неотделима от owner-ветки без риска (см. п.1
   выше), это явно документируется как "оставлено как есть" в
   `docs/DECISIONS.md`, а не молча переносится с недосмотром.

# Обработка персональных данных

Дата: 2026-07-31. Технический документ — описывает, что код РЕАЛЬНО делает,
не юридические обещания. Формулировки про GDPR/сроки хранения как правовые
обязательства должен утверждать владелец бизнеса, не этот документ.

## Какие персональные данные собираются

| Тип данных | Где хранится | Кто видит | Цель | Входит в backup | Отправляется вовне |
|---|---|---|---|---|---|
| Telegram ID, имя (first_name/last_name/username) | `roles.json`, `worker_profiles.json`, все JSON-сторы, где есть `user_id` | Owner видит всех; Worker видит имена коллег в общих экранах (Команда, feed, чат) | Идентификация пользователя, авторизация | Да | Telegram (сам ID приходит от Telegram) |
| GPS-координаты (начало/конец смены) | `checkin_meta.json` (`start_lat/start_lon/finish_lat/finish_lon`) | Owner всегда; Worker — только свои | Подтверждение присутствия на объекте при check-in/check-out | Да | Нет |
| Время смен (start_at/finish_at, паузы) | `checkin_meta.json` | Owner всегда; Worker — только свои | Расчёт часов, табель | Да | Нет |
| Фотографии (начало/конец смены, объекты, дефекты, аватар) | `checkin_photos/`, `object_photos/`, `avatars/`, `feed_photos/` (mangel-фото тоже здесь) | Зависит от контекста — фото объекта видят все авторизованные, фото профиля владелец файла + owner, фото смены — owner + сам работник | Подтверждение выполненной работы, визуальная фиксация дефектов, идентификация в профиле | Да | Нет |
| Текст сообщений чата | `chat_messages.json`, `chat_messages_archive.json` | Участники конкретного треда (группа/DM/object/mangel/task) + owner всегда | Коммуникация команды | Да | Нет (кроме best-effort AI-анализа фото по явному запросу owner, см. ниже) |
| Голосовые сообщения + их транскрипт | `chat_attachments/` (аудио-файл), поле `voice_transcript` в сообщении чата, отдельно `transcribe_audio/{uid}/` | Те же правила доступа, что у остального контента (участники треда) | Голосовой ввод для чата и для finish-shift wizard | Да | Аудио отправляется на локальную модель faster-whisper (на этом же сервере, не внешний API) для транскрипции |
| Отсутствия (тип, период, причина) | `abwesenheit.json` | Owner всегда; Worker — только свои | Учёт отпусков/больничных | Да | Нет |
| Профиль (навыки/skills, размеры одежды, день рождения) | `worker_profiles.json` | Owner всегда; сам работник — свой профиль; коллеги — частично (имя видят все, день рождения показывается в общем feed как поздравление) | Учёт квалификации для назначений, поздравления с ДР, снабжение спецодеждой | Да | Нет |
| Telegram ID (журнал инструментов) | `mangel_tickets.json` (created_by/assigned_worker_id) + Google Sheets (инструменты — `tools_lib.py`, поле "ID держателя") | Owner всегда; текущий держатель инструмента — свои данные видит через карточку | Учёт кто взял/держит инструмент, история выдач | Да (JSON-часть); Google Sheets — отдельная защита у Google | Google Sheets (см. ниже) |
| Дефекты (описание, фото, комментарии) | `mangel_tickets.json`, фото в `feed_photos/` с префиксом `mangel_` | Все авторизованные (owner-решение: "любой worker видит любой дефект") | Учёт качества, коммуникация по проблемам | Да | Нет |

## Внешние сервисы, куда уходят данные

- **Google Sheets** — объекты, этапы, инструменты (не персональные данные
  сотрудников напрямую, но содержат Telegram ID держателя инструмента и
  ссылки на имена в комментариях к этапам). Доступ через OAuth refresh_token,
  защита — стандартная защита Google-аккаунта владельца + права доступа к
  конкретной таблице.
- **Telegram** — сам факт использования приложения идёт через Telegram Bot
  API (initData авторизация), Telegram видит, что пользователь открыл Mini
  App, но НЕ видит содержимое запросов внутри приложения (та часть — прямой
  HTTPS к серверу Promonta, не проксируется через Telegram).
- **AI API (GLM/Claude)** — используется в `/api/ai-chat` (owner-only чат с
  AI-ассистентом) и в AI-анализе фото check-in (`analyze-progress`/
  `analyze-materials`/`analyze-defects` — owner или сам работник запрашивает
  анализ СВОИХ фото смены). В обоих случаях данные (текст сообщения или фото
  смены) отправляются во внешний AI API по явному действию пользователя, не
  автоматически на каждую загрузку.
- **faster-whisper** — локальная модель на этом же сервере (CPU), голосовые
  НЕ отправляются во внешний сервис для транскрипции.
- **Сервер/хостинг** — Hetzner VPS, все JSON-сторы и файлы загрузок физически
  на этом одном сервере (см. `docs/BACKUP_AND_RECOVERY.md` для деталей backup).

## Срок хранения

**OWNER DECISION REQUIRED** — на момент этого документа явной ретеншен-политики
для персональных данных НЕТ. Фактическое поведение кода:

- Чат: подтверждено чтением кода (`_purge_old_chat`, вызывается на каждый
  `GET /api/chat/messages`) — сообщения старше `CHAT_RETENTION_SECONDS` (7 дней)
  РЕАЛЬНО переносятся из рабочего `chat_messages.json` в
  `chat_messages_archive.json` при следующем чтении чата. Это архивирование
  (append-only), не удаление — сообщение продолжает физически существовать в
  архиве бессрочно, просто перестаёт быть "активным" в интерфейсе. `CHAT_MAX`
  (отдельная константа) дополнительно ограничивает размер рабочего файла по
  количеству сообщений тем же архивирующим механизмом.
- Фото смен/объектов/дефектов — хранятся бессрочно, нет автоматического
  удаления по возрасту.
- GPS-координаты — хранятся вместе с записью check-in бессрочно (та же
  запись, что и время смены — нет отдельного более короткого срока для GPS).
- Профиль (навыки/размеры/день рождения) — хранится, пока запись пользователя
  существует в `roles.json`/`worker_profiles.json`.

## Способ удаления

**Технически существующая возможность (уже вписывается в текущий код):**

`DELETE /api/roles/{target_user_id}` (owner-only, `main.py`) — убирает роль
пользователя из `roles.json`. После этого:
- Пользователь больше не проходит whitelist-проверку в `get_current_user` —
  теряет доступ к приложению полностью (401/403 на все запросы).
- **НЕ удаляет** сами данные — профиль в `worker_profiles.json`, история
  чата, фото, записи о сменах/отсутствиях остаются на диске. Это соответствует
  паттерну "деактивация доступа", не "удаление персональных данных" — тот же
  принцип, что уже применяется к удалённым тредам чата (`_archive_chat_messages`
  — комментарий в коде явно: "удаление треда/сообщения не должно стирать
  историю безвозвратно").

**Чего технически НЕТ (не добавлено в рамках этого release — было бы новой
крупной функцией, выходит за FEATURE FREEZE):**
- Отдельного endpoint "полностью стереть все данные пользователя X" (right to
  be forgotten в строгом смысле).
- Автоматического анонимизирования исторических записей (чат/фото) после
  увольнения сотрудника.

Если владельцу нужна полная функция удаления персональных данных по запросу —
**OWNER DECISION REQUIRED**: это отдельная задача вне текущего release-цикла
(затрагивает много JSON-сторов сразу, требует продуманного решения что делать
с чужими ссылками на удаляемого пользователя в чужих данных — например,
сообщение другого работника, отвечающее на сообщение удаляемого).

## Что НЕ делает эта система (явно, чтобы не создавать ложных ожиданий)

- Не шифрует JSON-файлы на диске отдельно от файловой системы сервера в
  целом (обычные файлы, читаемые с правами root/promonta пользователя).
- Не имеет отдельного консент-экрана при первом входе, объясняющего сбор GPS/
  фото — доступ выдаётся владельцем вручную через whitelist, предполагается,
  что это внутренний инструмент компании, сотрудники информированы вне
  приложения (трудовой договор/устное объяснение) — это организационный, не
  технический факт, отдельно от кода.
- Не логирует доступ к персональным данным отдельно от общего `audit.log`
  (тот логирует method/path/user_id/status, не "кто открыл чей профиль" как
  отдельное поле).
